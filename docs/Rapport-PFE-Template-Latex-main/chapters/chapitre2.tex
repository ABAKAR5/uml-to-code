\section{Choix du Cycle de Vie}
%=============================================================

\subsection{Définition du cycle de vie}

Le cycle de vie de développement d'une application représente la période de temps qui recouvre la vie d'une application : sa naissance, sa construction, son exploitation, sa maintenance et son retrait. Le choix du cycle de vie est une décision fondamentale qui détermine la manière dont les activités de développement sont organisées et enchaînées dans le temps.

\subsection{Comparaison des cycles de vie}

Plusieurs modèles de cycle de vie existent, chacun adapté à des contextes spécifiques. Le tableau ci-dessous présente une comparaison des principaux modèles :

\subsection{Modèle Incrémental — Justification}

Le modèle de cycle de vie retenu pour ce projet est le \textbf{modèle incrémental}. Ce choix est motivé par trois raisons principales :

\begin{itemize}
    \item \textbf{Durée courte du projet} : trois semaines de développement nécessitent des livraisons rapides et concrètes à chaque étape
    \item \textbf{Projet réalisé en solo} : les cycles nécessitant une équipe (comme Scrum) ne sont pas adaptés à un développeur unique
    \item \textbf{Incertitudes techniques} : l'intégration de l'IA générative (Groq) et des interfaces avancées (Monaco Editor) impose un ajustement progressif
\end{itemize}

Le modèle incrémental permet de construire le système par couches successives. Chaque incrément produit une version fonctionnelle et testée du logiciel, enrichie de nouvelles fonctionnalités. Contrairement au modèle en cascade, il permet de valider les choix techniques tôt et d'ajuster la trajectoire si nécessaire.

\section{Architecture Globale du Système}
%=============================================================

\subsection{Vue d'ensemble}

Le système UML-to-Code suit une \textbf{architecture client-serveur en 3 couches} :

\begin{itemize}
    \item \textbf{Couche Présentation} : Interface React.js avec design Glassmorphism, Monaco Editor, historique localStorage, thème sombre/clair et animations
    \item \textbf{Couche Métier} : Serveur Flask Python assurant l'orchestration, le parsing XMI/image/PDF, l'appel à l'API Groq et la génération ZIP
    \item \textbf{Couche IA} : API Groq (Llama 3.3-70b) assurant la génération intelligente du code Python, PHP et Flask
\end{itemize}

\subsection{Diagramme de Classes}

\subsubsection{Définition}

Le diagramme de classes est le diagramme le plus important pour les méthodes d'analyse orientées objet. Il permet de spécifier \textbf{QUI intervient} à l'intérieur du système et représente une vue statique du système d'information. Il modélise les classes, leurs attributs, leurs méthodes et leurs relations.

\subsubsection{Description des classes}

Les classes principales du système sont :

\begin{itemize}
    \item \textbf{XMIParser} : responsable du parsing des fichiers XMI et de l'extraction des classes UML
    \item \textbf{FileUploadHandler} : gère l'upload, la validation et la détection du format des fichiers
    \item \textbf{UMLClass, UMLAttribute, UMLMethod} : le modèle de données représentant un diagramme UML parsé
    \item \textbf{GroqClient} : client de l'API Groq pour la génération de code par IA
    \item \textbf{BaseGenerator} : classe abstraite dont héritent \textit{PythonGenerator} et \textit{PHPGenerator}
    \item \textbf{FlaskServerGenerator} : génère automatiquement le serveur Flask avec routes CRUD
    \item \textbf{ZipGenerator} : regroupe le code et le serveur Flask dans une archive ZIP
\end{itemize}

\subsection{Diagramme de Séquence}

\subsubsection{Définition}

Le diagramme de séquence permet de valider les cas d'utilisation et de comprendre la logique de l'application. Il met en évidence les objets et leurs interactions d'un point de vue temporel, modélisant \textbf{COMMENT le système réalise} les cas d'utilisation.

\subsubsection{Diagramme de séquence — Génération de code}

Le diagramme ci-dessous décrit le flux complet d'interaction lors d'une génération de code, depuis l'upload du fichier jusqu'à l'affichage du résultat dans le Monaco Editor :

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{SD_Generation_Code.jpg}
    \caption{Diagramme de séquence — Génération de code}
\end{figure}

Les étapes clés du processus sont :

\begin{enumerate}
    \item L'utilisateur uploade un fichier via l'interface React
    \item Le frontend envoie une requête POST à l'API Flask
    \item Le \textit{FileUploadHandler} détecte le format du fichier
    \item Si XMI : le \textit{XMIParser} extrait les classes et attributs
    \item \textit{FileUploadHandler} retourne le format et chemin du fichier à Flask
    \item Si image/PDF : le fichier est envoyé au \textit{GroqClient} pour analyse visuelle
    \item Le \textit{GroqClient} construit le prompt et appelle l'API Groq
    \item Le \textit{BaseGenerator} génère le code Python ou PHP
    \item Le code final est retourné à l'interface et affiché dans le Monaco Editor
\end{enumerate}

\section{Conception Détaillée des Modules}
%=============================================================

\subsection{Module de Parsing XMI}

Le module de parsing XMI est le cœur algorithmique du système. Il utilise la bibliothèque native \texttt{xml.etree.ElementTree} de Python pour analyser les fichiers XMI exportés depuis StarUML. Le processus se déroule en plusieurs étapes :

\begin{enumerate}
    \item \textbf{Lecture et parsing} du fichier XMI
    \item \textbf{Extraction des classes} : nom, identifiant, classe parente (héritage)
    \item \textbf{Extraction des attributs} : nom, type, visibilité (public, private, protected)
    \item \textbf{Extraction des méthodes} : nom, paramètres, type de retour, visibilité
    \item \textbf{Construction} d'une liste d'objets \texttt{UMLClass} utilisables par les générateurs
\end{enumerate}

\subsection{Module de Génération de Code}

La génération de code repose sur une hiérarchie de classes utilisant le patron de conception \textbf{Template Method}. La classe abstraite \texttt{BaseGenerator} définit le squelette de l'algorithme de génération, tandis que \texttt{PythonGenerator} et \texttt{PHPGenerator} fournissent les implémentations spécifiques à chaque langage.

Pour chaque classe UML extraite, le générateur produit :
\begin{itemize}
    \item Le \textbf{constructeur} avec initialisation de tous les attributs
    \item Les \textbf{getters} et \textbf{setters} pour chaque attribut
    \item La \textbf{gestion de l'héritage} (\texttt{extends} en PHP, héritage Python)
    \item Les \textbf{commentaires} de documentation
\end{itemize}

\subsection{Module IA — GroqClient}

Le \texttt{GroqClient} est responsable de la communication avec l'API Groq. Pour les fichiers XMI, il reçoit une description textuelle des classes extraites et génère un code enrichi et contextuel. Pour les images et PDF, il exploite les capacités de \textbf{vision} du modèle Llama 3.3-70b pour analyser directement le diagramme visuel.

Le prompt envoyé à l'API est construit dynamiquement par la méthode \texttt{buildPrompt()} qui inclut :
\begin{itemize}
    \item La liste des classes avec leurs attributs et méthodes
    \item Le langage cible (Python ou PHP)
    \item Les instructions de formatage du code généré
\end{itemize}
